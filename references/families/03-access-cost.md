# Семейство 3 · Доступ, контуры и деньги

Кто может дёрнуть агента, нажать чужую кнопку, утащить контекст из другого чата и сжечь деньги.
Родственно OWASP Top 10 for Agentic Applications 2026 (ASI03 identity & privilege abuse,
ASI06 memory/context poisoning, ASI08 cascading failures) — но проверяем не абстрактно,
а по персонам из карты.

## Что проверять

1. **Кто пропускается.** Правило «команды» в коде (allow-list логинов, `getChatMember`,
   владелец по id) и где оно применяется: в личке, в группах, в callback, в войсах, в кронах.
   Типовая дыра: проверка есть в личке, в группах нет — любой участник любой группы с ботом
   получает полный вызов движка.
2. **Чужая рука.** Callback-хендлеры: сверяется ли `cb.from_user` с автором запроса или
   владельцем. Кнопки в группе видит весь чат. Пакет действий может содержать удаление.
3. **Изоляция контуров.** Вопрос из клиентского чата подмешивает переписку командного;
   `/summary` в чужой группе выкладывает сводку по всем чатам; личка попадает в общий индекс;
   фрагменты памяти отдаются без проверки членства в чате-источнике; страницы вики и документы
   без фильтра. Таблица чатов должна знать «свой/клиентский», а не только id.
4. **Шлюзы согласования.** Действия с внешними последствиями (пост в чат, правка доски,
   рассылка, создание созвона, удаление) учитывают полномочия, последствия и уже данную авторизацию.
   При существенной неоднозначности сначала уточнение; не выполняй конфликтующее действие
   автоматически. Не требуй повторное подтверждение уже разрешённой операции без причины.
5. **Деньги.** Лимит вызовов на человека в день; лимит на день у платных API (транскрибация,
   зумы); согласованность бюджета вызова с задачей и ограничениями; что при 402 (нет денег): алерт
   владельцу или тихий уход. **Молчаливый фолбэк** на другой платный движок скрывает и обрыв связи,
   и кончившиеся деньги — расходы просто переезжают на другой счёт.
6. **Троттлинг.** Повтор одного вопроса, спам войсами, бесконечный цикл крон → движок → ошибка → крон.
7. **Хардкоды.** Username владельца в проверках (`== "owner_login"`), гейт одной функции
   переиспользован для другой (гейт зумов для запуска планирования).
8. **Кэши членства** без TTL: убрали человека из чата — он всё ещё «свой».
9. **Секреты.** Токены в репозитории, в логах, в алертах с сырым текстом ошибки. Читать `.env`
   для проверки нельзя — проверять защиту и обезличенные результаты сканера; не выводить значения секретов
   из истории git или логов.

## Где искать

`_from_team`, `is_team`, `get_chat_member`, `owner_chat_id`, `@router.callback_query`
(есть ли проверка `from_user`), `messages_for_day(cfg.team_chat_id` в ответах из любого чата,
`max_tokens=`, `except EngineError` → второй провайдер, `check_balance`, `daily_limit`,
`zoom_allowed`.

## Прецеденты

- Планировщик v0.26.0: доступ по списку логинов и только в личке; «в любой группе, где состоит бот,
  позвать его и потратить запрос к движку мог кто угодно»; вопрос из клиентского чата тянул день
  главного чата; `/summary` в клиентской группе вываливал сводку по всем чатам.
- Планировщик до v0.26: кнопка «✅ Применить» не проверяла нажавшего; `requested_by` писалось, но не
  читалось; пакет мог содержать delete.
- Планировщик v0.26.0: «Отказ DeepSeek больше не уезжает молча в Codex».
- Планировщик v0.4.1: нотетейкер приходил в пустую комнату — «три пустые записи по одиннадцать минут».
- Библиотекарь v1.1.0: очередь фото общая на всех — «фото одного участника может уехать в каталог другого».

## Типовые лечения

Единая функция членства с TTL, применяемая во всех входах; `requested_by_id` + TTL у пакетов;
`chats.kind`; контекст ответа из чата, где спросили; лимит на человека в день с алертом;
фолбэк только явный и с сообщением; секреты только в Keychain/.env.
