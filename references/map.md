# Карта агента

Карта — общий навигатор инспекторов и судьи; держи её компактной (ориентир 150 строк).
Каждый факт имеет источник: код, документ, наблюдение или артефакт. Её строит оркестратор или выделенный исследователь; экстрактор — вспомогательный
источник для Python. Запуск: `python3 <корень-скилла>/scripts/extract_promises.py <мишень> --md --full`.
Статистика извлечения не является полнотой обещаний.

Карта сохраняется в `docs/audits/map.md` мишени. При повторной ревизии субагент получает
прошлую карту и обновляет её по диффу, а не строит заново: так дешевле и видно, что изменилось.

## Обязательные разделы

### 1. Стек и цены
- Фреймворк и версия (aiogram 3.x / python-telegram-bot / telebot / FastAPI / MCP stdio), способ
  получения апдейтов (long polling / webhook), планировщик (APScheduler / cron / systemd timer).
- Хранилище: SQLite (путь, таблицы одной строкой), Postgres, файлы, git-репозиторий как база.
- Внешние платные сервисы: движок LLM (модель, задачи, лимит токенов на вызов, таймауты),
  распознавание речи, API досок/CRM, поиск. Для каждого: где вызывается, есть ли лимит на день,
  что происходит при 402/429/500/таймауте, есть ли фолбэк на другой платный сервис.
- Деплой и прод: юнит systemd, пользователь, путь, скрипт обновления, есть ли окно «не деплоить»
  (созвон, крон), алерт при падении (`OnFailure=`).

### 2. Точки входа (кто может дёрнуть)
Таблица: вход · где в коде · кто пропускается фильтром · что запускается дальше.
- Команды `/x` и `/start` с deep-link payload.
- Кнопки: callback-префиксы (`act:`, `plan:`, `tr:`), в каких чатах живут сообщения с кнопками,
  проверяется ли нажавший, есть ли срок годности.
- Обращения по имени, @упоминание, reply на сообщение бота — читается ли `reply_to_message`.
- Войсы, фото, документы, альбомы, пересланные сообщения.
- Кроны и джобы: время, что шлют, куда, что делают при ошибке, есть ли отметка последнего запуска.
- Вебхуки и внешние события (Fireflies, Zoom, платёжки).

### 3. Персоны
Используй роли, знания, потребности и разрешения. Реальные имена необязательны, не
собирай лишние персональные данные. Для каждой роли: что разрешено и обещано, типовые
задачи, среда использования. Новичок и возвращающийся пользователь — разные сценарии.
Для фоновой задачи укажи получателя и ответственного за восстановление.

### 4. Состояние
- FSM: состояния, где `set_state` без очистки данных, где `state.clear()`, единый вход/выход в диалог.
- Глобальные структуры на процесс (очереди, кэши, `pending`), переживают ли рестарт, общие ли на всех.
- Таблицы «ожидающих» сущностей (actions, pending_photos): статусы, срок годности, кто может применить.

### 5. Поток данных
Схема «собрал → сохранил → проиндексировал → достал» по каждому типу информации
(сообщения, транскрипты, документы, страницы вики). На каждой стрелке: фильтры, потолки
(`[:4000]`, `limit=120`, «≥4 сообщений»), окна времени, что теряется молча.

### 6. Корпус обещаний (три слоя)
- Слой 1, из `extract_promises.py`: команды, подписи кнопок, тексты ответов, константы. Указать
  долю «не смог разрешить» из вывода скрипта.
- Слой 2, промпты и персона: файлы `prompts.py`, `persona.py`, `texts.py`. Для каждого шаблона одной
  строкой: какие действия модель может пообещать («сейчас напишу команде», «внесу правки») и есть
  ли под них инструмент в коде. Плюс README, ТЗ, /help, описание в BotFather (если доступно).
- Слой 3, реальные ответы бота: есть ли таблица с ответами бота (например, `messages` с его id)
  — путь и способ выборки для проб. Это же — точка чтения полного ответа для живого прогона:
  как прочитать текст, который транспорт не отдаёт (rich-сообщения, документы), только чтение.

### 7. Области для инспекторов
Выдели связанные компоненты по рискам и зависимостям, а не по числу строк. У каждого
сквозного сценария один ответственный за путь целиком. Запиши границы, общий код и
обязательства по передаче находок между областями. В маленькой системе работай последовательно.

### 8. Закрыто архитектурно
Что из семейств уже закрыто конструкцией и не надо искать заново: алерт при падении юнита,
единый вход в диалог, «публичные тексты пишет только владелец», роутер-страж, нормализация имён.
С путём к коду — судья будет проверять.

### 9. Известные грабли
Из CLAUDE.md, `docs/history.md`, комментариев в deploy-скриптах, последних 10 записей CHANGELOG:
одной строкой каждая, с датой. Инспекторы проверяют, не вернулись ли они.

### 10. Транспорт для живого прогона
Чем аудитор может пройти сценарии как пользователь: Telethon-сессия и @имя бота, CLI-бинарь,
HTTP/MCP-клиент; какие аккаунты/роли доступны; стенд или прод; тестовые сущности; тарифы
движка для замера стоимости; какие сценарии прогнать нельзя и почему (`live-drive.md`).

## Профиль стека по умолчанию: aiogram 3 + SQLite + systemd

Так устроены боты, на которых скилл обкатан. Опорные точки для поиска в коде:
`Router()`, порядок `include_router`, `@router.message(F.text == …)`, `Command(`, `CommandStart(`,
`@router.callback_query(F.data.startswith(`, `state.set_state` / `state.clear` / `update_data`,
`InlineKeyboardButton(text=`, `KeyboardButton(`, `answer(` / `reply(` / `send_message(` /
`edit_text(` / `send_rich_message(`, `AsyncIOScheduler` / `add_job`, `aiosqlite.connect` /
`sqlite3.connect`, `except Exception` (общие ловушки), `asyncio.wait_for` (таймауты),
`getChatMember` / `get_chat_member` (членство). Не опирайся на раскладку папок: где-то всё
в одном файле на 3 тыс. строк, где-то `handlers/ services/ texts.py`.

## 11. Результаты и наблюдение

Для каждого обещанного результата: формат, рендерер, клиент/устройство, эталон/критерии,
где открыть/скачать/исправить, доступные примеры и разрешённая тестовая среда.
Матрица: S-id → обещание → входы/компоненты → выход → ответственный → шесть осей/методы.
Общая функция не считается проверенной для всех сценариев без проверки условий её вызова.
