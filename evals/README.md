# Проверка аудитора

`evals.json` — синтетические сценарии поведения. Не выдавать их за аудит реального продукта.
Запусти каждый в отдельном контексте с текущим SKILL.md и нужными references; сравни с
сохранённой предыдущей версией на одинаковых входных данных. Запиши ответы и оцени
expectations: pass/fail с цитатой из ответа, а не по намерению инструкции.

Для visual_observed нужен реальный доступный снимок фикстуры: описание PDF само по себе
не проверяет способность агента видеть. Без фикстуры это только проверка рассуждения,
визуальную часть считать не выполненной. Для clean также нужен положительный отрисованный
образец для полноценной визуальной оценки. Храни артефакты в workspace оценки, не в проде.

Минимальный порог: основные дефекты и все существенные находки сохранены; нет ложного
обвинения в owner_pilot/clean; visual_unknown честно ограничен; сравнение пути конкретно.
Кейсы 9–11 проверяют живой прогон: обязательность при возможности, план до прогона,
границы транскрипта. Дополнительно проверь три запроса на активацию (аудит бота, неудобный агент, красота вывода
программного агента) и три исключения (аудит поста, улучшение скилла, только стиль кода).
Статическая проверка description не равна проверке автоматической активации в новой сессии.

Регрессионные проверки скриптов: `python3 -m unittest discover -s tests -v`.
Публикуй фактическое число проверок и ограничения; не заявляй end-to-end проверку продовых
ботов по синтетическим кейсам.
